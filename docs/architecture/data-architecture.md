# Data Architecture & Conceptual Data Model

> **Status:** Architecture Design / Pre-Implementation Baseline
> **Database:** PostgreSQL (System of Record)

---

## 1. Data Design Principles

QueueLess Bharat's data architecture is built around relational integrity, historical durability, transparency, and data minimization:

1. **Queue Events as Durable Historical Facts:**
   Raw events representing physical transitions (counter opened, ticket issued, citizen entered service, ticket completed) are treated as immutable, append-only records. Historical events are never updated or deleted during standard operations.
2. **Strict Separation of Estimates from Observations:**
   Calculated wait-time estimates are derived analytical outputs, strictly partitioned from primary observations and events. If an estimation algorithm changes, historical observations remain untainted.
3. **Comprehensive Estimate Provenance:**
   Every persisted estimate preserves its computational context: lower bound, upper bound, expected value, confidence rating, sample size, freshness timestamp, and the specific estimator algorithm/version that produced it.
4. **Auditability & Traceability:**
   The platform can demonstrate precisely which input events, observations, and algorithmic parameters produced any given estimate at any point in time.
5. **Data Minimization & Privacy:**
   The system deliberately avoids collecting or storing sensitive personal data. Citizen queue observations track crowd counts, service categories, and timestamps—never Personally Identifiable Information (PII) like Aadhaar numbers, full physical addresses, or detailed medical records.

## 2. Conceptual Entities & Roles

The conceptual domain model consists of the following primary entities:

### 1. `users`
Represents platform actors, including general citizens submitting crowd observations, registered counter operators, and system administrators. Stores minimal identity metadata (authentication identifiers, roles, reputation/trust weight metrics) with zero unnecessary personal attributes.

### 2. `locations`
Represents physical public service institutions (e.g., "District Hospital Civil Lines", "Regional Transport Office South Zone", "Sub-Divisional Magistrate Office"). Contains geographic coordinates, facility type, operating hours, and active administrative status.

### 3. `services`
Specific operational queues or offerings conducted within a location (e.g., "OPD Registration", "Driving Licence Renewal", "Caste Certificate Verification"). A single location offers multiple distinct services, each with its own baseline service duration and operational schedule.

### 4. `counters`
Physical or logical service windows dedicated to one or more services at a location (e.g., "Counter 1 - Fee Deposit", "Window 4 - Biometrics"). Captures operational state (open, closed, paused, staff break) and current active staff assignments.

### 5. `queue_sessions`
Represents a continuous operating cycle of a queue for a specific service at a location across an operational window (e.g., the morning session of August 15th for OPD Registration). Acts as an aggregate root for grouping related events and calculations within an active working day.

### 6. `queue_events`
Immutable event stream recording transactional state changes within a `queue_session` (e.g., `SESSION_OPENED`, `TICKET_DISPENSED`, `COUNTER_PAUSED`, `COUNTER_RESUMED`, `SESSION_CLOSED`). Provides an append-only audit log of physical queue progression.

### 7. `service_sessions`
Represents the individual transaction lifecycle for a specific person or ticket served at a specific counter (e.g., `ticket_called_at`, `service_started_at`, `service_completed_at`, `outcome`). Used to compute empirical service duration metrics and counter throughput rates.

### 8. `wait_observations`
Point-in-time observations contributed by citizens or operators regarding queue conditions (e.g., estimated people in line, line physical length, observed wait duration, counter activity). Captured with reporter trust tier, submission timestamp, and source channel (direct web form vs. AI natural-language parsed update).

### 9. `estimates`
Derived output generated by the deterministic queue engine for a specific `service` and `queue_session`. Captures:
- `expected_wait_minutes`: Deterministic median/mean prediction.
- `lower_bound_minutes`: Optimistic wait boundary.
- `upper_bound_minutes`: Conservative wait boundary.
- `confidence_score`: Metric indicating certainty (e.g., high, medium, low based on sample size and variance).
- `sample_size`: Number of recent observations/events informing the estimate.
- `freshness_timestamp`: Timestamp of the latest underlying signal.
- `algorithm_version`: Identifier for the mathematical estimator model used.
- `computed_at`: Exact generation timestamp.

## 3. Entity Relationships (Conceptual)

```
[ locations ] 1 ──── * [ services ]
      │                     │
      │ 1                   │ 1
      ▼ *                   ▼ *
 [ counters ] 1 ──── * [ queue_sessions ]
                             │
            ┌────────────────┼────────────────┐
            │ 1              │ 1              │ 1
            ▼ *              ▼ *              ▼ *
     [ queue_events ] [ service_sessions ] [ wait_observations ]
                             │                     │
                             └──────────┬──────────┘
                                        │ (Input signals)
                                        ▼
                                  [ estimates ]
```

### Relationship Rules
- A **Location** has many **Services** and many physical **Counters**.
- A **Queue Session** represents an operational run of a **Service** at a **Location** during a given time period.
- **Queue Events** and **Service Sessions** belong to a **Queue Session**, recording ground-truth operational transitions.
- **Wait Observations** are submitted against a **Service** / **Location** by **Users** (or anonymous visitors with trust weight).
- **Estimates** are periodically computed for a **Service** and linked to the active **Queue Session**, referencing the latest pool of observations and service session throughput.

---

## 4. Lifecycle & Retention Strategy

- **Live Operational Data:** Active `queue_sessions`, recent `wait_observations`, and the latest `estimates` serve hot client polling requests.
- **Historical Analysis:** Immutable `queue_events` and historical `service_sessions` are retained long-term to train baseline statistical distributions (day-of-week patterns, hour-of-day seasonalities) and ensure audit integrity.
- **Estimate Invalidation:** Estimates expire automatically based on a freshness decay curve. If no new observations or events are recorded within a defined freshness window, confidence degrades explicitly, prompting users with freshness indicators rather than presenting stale data.
